# N-339: resume a job run from where it stopped (CLI, TUI, dbc web)

Session: `edec9ba6-164e-4aee-a830-924fea518135`

## Ask

"Next list item N-339", then `/sw`. N-339 was the part of N-336 not done:
re-running a job always starts at the root. Steps hand each other nothing
in memory (each pipeline reads and writes databases and files), so a step
that succeeded has usually left its output in place. The item sketched
`dbc job run <job> --resume <run-id|last>` and a Resume in the TUI's and
dbc web's Runs views, and listed five questions to settle first.

## Decisions (the user's)

Asked with AskUserQuestion after reading `jobs/job.go` (`executeJob`'s
readiness walk), `jobs/records.go`, `jobs/engine.go` (`runVars`) and
`pipeline/run.go`. Two facts shaped the options. `${run.*}` reaches every
node's config, not only step params. And every step already runs on its
own session (`runOne` → `sdb.New`), so a temp table never reliably
reached a later step.

| Question | Picked |
|---|---|
| Run values | **All of the first run's**: `id`, `date`, `time`, `started` (down a chain of resumes too); `trigger` is the resume's own |
| Reuse rule | **Only if unchanged**: same step id, same pipeline, same pipeline-spec hash (newly stored), same substituted params, and every after reused. `-p` allowed; what it changes re-runs with everything after it. A record without a hash re-runs |
| Outputs that do not last | **Trust the user, plus `--rerun STEP,…`** |
| The record | **New status `reused` ↻** with `reused_from`, no rows counted; the run gets `resumes` and `by` "resumes ID" |

## Part 1: engine and CLI (`9b9bc5c`)

New `jobs/resume.go`, with a doc comment and diagram:

- `earlierRun(job, id|last)` finds the run and checks it: a job run of
  that name that has ended (any status but running/queued; a succeeded
  run can be resumed, and re-runs only what was edited since).
- `earlierValues`: the earlier record's `RunValues` when it was itself a
  resume, else its id and start (`runVars`' rule).
- `resumeParams`: the earlier run's params, for names the job still
  declares, under the overrides. `jobParams` then adds new defaults and
  refuses undeclared overrides.
- `SpecHash`: the first 16 hex digits of the SHA-256 of `json.Marshal(spec)`
  (map keys sorted; a Go func's `Fn` is `json:"-"`).
- `substStepParams`, factored out of `runStep` (which now calls it).
- `resumePlan` walks the steps in `readinessOrder` (Kahn's, spec order
  for ties) and gives each a `reuse{from, fromID, why}`. `why` names why
  a step the earlier run finished runs again: `named in --rerun`,
  `after X, which runs`, `its pipeline is Y now, was X`, `… record has
  no hash …`, `pipeline X was edited since`, `its params differ:
  x: "1" → "2"`. `fromID` follows `ReusedFrom` down a chain.
- `markReused` sets a queued step reused: `ReusedFrom`, the params it ran
  with, its fragments reused, no counts.

`StartJob`'s pre-flight moved into `prepareJob`, which takes nothing and
changes nothing (check, params, pipelines loaded and hashed, and for a
resume the earlier run and the plan). A plan that runs nothing is refused:
"nothing to resume: every step of run X succeeded and is unchanged
(--rerun STEP runs one again)". New `Engine.CheckStart(req)` runs
`prepareJob` alone. `dbc job run --wait=false --resume …` calls it in the
parent, because the detached child would refuse with nobody to hear it
("the run did not start … run it with --wait to see why").

`executeJob` takes the plan. `waiting[s]` counts only the afters that
run, and `ready` is every running step whose afters are all reused (for a
fresh run that is the root, as before; the checker guarantees one root).
`resumeLines` opens a resume's log:

```
job nightly: resuming run 20261125-122546-77fa: reusing stage; running load, report, from load (2 at a time, cli)
[stage] ↻ stage: reused from run 20261125-122546-77fa
[report] report runs again: pipeline report was edited since
```

`runVars` returns the record's `RunValues` for a resume.

Record fields: `Run.Resumes`, `Run.RunValues` (only on a resume; cloned),
`PipelineRun.SpecHash` (every job step), `PipelineRun.ReusedFrom`.
`pipeline.Reused` is the status. `userdata.RunHead.Resumes` is read off
the record's head for free (`runFile` embeds `RunHead`), and `summaryOf`
sets it for live runs. `glyph` ↻; `stepSummary` "copy ↻ reused, clean ✓ 7
rows"; `Tree` prints "reused from ID" and no counts (`notRun` covers
queued, skipped, reused). `dbc runs` shows a resume's trigger as
`cli (resumes ID)`. Only a resume's cell changes, so a CSV of the listing
reads as it did. (Putting `by` in every row, as `Tree`'s head does, would
have changed scheduled rows' cells.)

CLI: `--resume RUN|last` and `--rerun` (a StringSlice, so comma-separated
or repeated). `resumeFlags` trims, refuses an empty step name, a
non-id/non-`last`, and `--rerun` without `--resume` (exit 2). Engine
refusals exit 1. `job run`'s own flags are not in `cats-plugin.toml`'s
completions: the manifest test covers top-level command flags only, and
`--param`/`--wait` aren't listed either.

## Part 2: the TUI (`6c524a0`)

`r` in the Runs list (Alt+J) and in the run monitor calls
`Model.resumeRun(id)`. It reads the record (`m.jobs.Get`), refuses a
pipeline run or one still going, and loads the job with
`jobs.LoadJob(cfg.JobsDir, cmpOr(r.Source, r.Name))`. Using `LoadJob`
rather than `cfg.FindJob` keeps a file of that name in the cwd from being
picked. It then starts the job with `Resume` and `By: "terminal"`, and
the new run's monitor opens (`started`). A refusal lands in the modal's
note and the log. `runGlyph` ↻ (muted, as skipped); `rowFacts` treats
reused like queued/skipped and adds "reused from ID". The list's desc adds
`↻ resumes ID`; the monitor's footer offers `r resume` on an ended job
run. The monitor's header already reads `manual (terminal, resumes ID)`
through `By`.

## Part 3: dbc web (`b18af86`)

- `POST /api/v1/jobs/:name/run` takes `resume` and `rerun` (`jobRunReq`).
  Refusals are 400s.
- `runs.js`: `STATE.reused = "↻"`; `NOTRUN(s)` replaces the scattered
  `queued || skipped` checks. ↻ Resume (`data-act="resume"`) shows on an
  ended job run when the host has `resume`. It disables itself, calls
  `host.resume(r)`, opens the new run's page, and logs a refusal.
  `runLink(id)` buttons (`data-act="openrun"`): "resumes run ID" under the
  header (plus the first run's id down a chain), and "reused: run ID ran
  it, and this run took its output over" in a reused step's section. The
  list's trigger cell gets " ↻" with a title.
- `app.js` `runsKit.resume`: POSTs for `r.source || r.name + ".json"`,
  with `ws` set to the job's open tab, as its ▶ Run would.
- `jobs.js` card: reused shows its state word. CSS:
  `.dcard.s-reused { opacity: .8; border-left-style: dashed; border-left-color: var(--accent) }`.
