# N-190: a pipeline's relative file paths resolve against `files_dir`

Session: `e8cdf162-5e00-42cf-b546-2b586d62c40e`

## Ask

1. N-190 (from the cats-todo backlog): a relative `path` in `csv.read`,
   `jsonl.read`, `csv.write` and `jsonl.write` resolved against the
   process's working directory. That was the shell's for `dbc pipeline
   run`, but wherever dbc web was started for dbc web and its scheduler.
   So a pipeline that worked from a shell wrote elsewhere, or failed, when
   scheduled. The item offered three fixes: a `files_dir`, the pipeline
   file's own directory, or a check warning on relative paths in a
   scheduled job's pipelines.
2. `/sw n190-files-dir`.

## Decision

One directory for every host: a new config key **`files_dir`**, default
**the home directory**.

| Option | Why not |
| --- | --- |
| The pipeline file's directory | Builder pipelines (`sdb.NewPipeline`) and the built-in examples have no file. Data would land among the specs in `pipelines_dir`, and a `jsonl.write` to `x.json` would show up as a broken pipeline. |
| A check warning only | Fixes nothing for dbc web's manual runs, and can't see a path that comes in through `${param}`. |
| `files_dir` beside the scripts (`~/.config/dbc/files`), as the other `*_dir` keys default | These are the user's files (an export to open, a download to load), and `~/.config` is hidden in Finder. |

Premise correction: the item said dbc.app's cwd "may be `/`". It isn't.
`macapp/DbcApp.swift` sets the helper's `currentDirectoryURL` to
`Paths.home`. So the home default keeps dbc.app's runs where they already
resolved, and brings the shell, dbc web and the scheduler into line with
it.

Precedent: `config/scripts.go` moved `scripts_dir` off cwd for the same
reason ("so every reader agrees whatever the cwd"), and `config/tls.go`
resolves `tls_*` against the config file rather than cwd.

The cost is the CLI. `dbc pipeline run` no longer reads a relative path
from the current directory, so a file there needs `-p in=$PWD/orders.csv`
or an absolute path. A checkout that wants project-relative paths sets
`files_dir = "."` in its `./dbc.toml`, which then means that checkout.

## How it flows

```
config.Load ─► Config.FilesDir (absolute; ResolveFilesDir)
   │
   ├─► jobs.Engine.runOne: opt.FilesDir = cfg.FilesDir (when unset)
   │     └─ dbc web, its scheduler, the TUI, `dbc pipeline run`
   │        (runPipelineHeadless goes through a jobs engine too)
   │
   └─► sdb.Paths.FilesDir (main.go headless scripts, workspace/run.go,
         jobs.Engine.paths for a node's session, jobs/script.go)
         └─ sdb.S.RunPipelineSpec: opt.FilesDir = s.paths.FilesDir (when unset)

pipeline.Options.FilesDir ─► runner.build ─► Env.filesDir (unexported)
   └─ Env.Path(p): "~"/"~/…" → home · absolute → as is
                   relative → filepath.Join(filesDir, p) · no filesDir → as written (cwd)
```

## Changes

- **`config/files.go`** (new): `DefaultFilesDir()` (home, or `.` when there
  is no home) and `ResolveFilesDir(raw, base)`, which follows `resolvePath`
  (`${VAR}`, `~`, relative to the config file's directory).
  `Config.FilesDir` (`files_dir`) is resolved in `resolveScripts`, the demo
  fallback included.
- **`pipeline/builtin_files.go`**:
  - `Env.Path(p)` is the one way a node turns a configured path into a file
    path.
  - `inFilesDir` and `isHomePath` are factored out of `expandPath`.
  - `pathErr` puts `(a relative path is in files_dir, <dir>)` in the
    message itself. It isn't a serr field because a node's error is shown
    by its text (`NodeStats.Error`, the run monitor), which a field doesn't
    reach. `jobs.errText` prints fields, but `SErr.Error()` doesn't.
  - `csvRead.Open`, `jsonlRead.Open` and `fileWrite.Open` (now taking `e`)
    go through `e.Path`; a failed mkdir gets the hint too.
  - The four `path` field docs and the header comment are rewritten.
- **`pipeline/node.go`**: `Env.filesDir` is unexported, so a plugin has a
  single way to a file (`e.Path`). This also kept sdb's API summary within
  its 14 KB budget. **`pipeline/run.go`**: `Options.FilesDir`, copied into
  each node's Env in `build`.
- **`sdb/pipeline.go`**: `Paths.FilesDir`; `RunPipelineSpec` defaults
  `opt.FilesDir` from it. The `Paths` doc was reworded shorter.
- **`jobs/engine.go`**: `runOne` sets `opt.FilesDir` from the config, and
  `paths()` carries `FilesDir`. **`jobs/script.go`**: `runOnOwnEngine`'s
  config gets `FilesDir` from the session's paths.
- **`main.go`**, **`workspace/run.go`**: script sessions' `Paths` carry
  `FilesDir`.
- **`scripts/plugins/wait_file.go`**: resolves its path with `e.Path`.
  **`pipeline/plugin.go`**: the SDK help line says a file path goes through
  `e.Path`.
- **`sdb/sdbapi/api.json`**: regenerated (`go generate ./sdb/sdbapi`).
- **Docs**:
  - README: the config block, the file plugins row, a paragraph under the
    plugin table, the plugin-author `e.Path` note, and "Pipelines headless".
  - `dbc.example.toml`.
  - `.claude/skills/dbc/SKILL.md` (use absolute or `$PWD/…` paths from a
    shell) and `scripting.md`.

### The API summary budget

`sdbapi.TestSummary` caps the assistant's sdb summary at 14 KB. It was at
14263 bytes, 73 under. The first version (`Env.FilesDir` exported, plus a
longer `Paths` first sentence) made it 14594. Unexporting the Env field and
tightening the `Paths` doc brought it to 14290, with 46 bytes of headroom.
I didn't raise the budget.

  - `TestEnvPath`: 10 cases, covering a relative path, a nested one, `../`,
    an absolute path, `~/`, `~`, `""`, an empty Env and a nil Env.
  - `TestFilesDirRun`: csv.write → csv.read → jsonl.write → jsonl.read, all
    on relative paths. Files land under `FilesDir`, the published paths are
    absolute, and nothing is created in cwd. A missing relative file's run
    error and `NodeStats.Error` both carry the hint; a missing absolute path
    doesn't mention files_dir.
  - `TestEngineFilesDir`: a scheduled-trigger run through the engine writes
    under `cfg.FilesDir`, not cwd, and `paths().FilesDir` is set.
  - `config/files_test.go` `TestFilesDir`: the resolution table, the demo

- Full suite: `go vet ./...` and `go test ./...` green, `gofmt -l` clean.
- Real binary (built to the scratchpad), with a temp config (`files_dir =
  "data"`, a SQLite connection) and the run started from a sibling
  directory:
  - `dbc pipeline run` wrote `data/exports/<run.date>.csv` beside the

  - The missing-file run printed `open …/cfg/data/nope/orders.csv: no such

  - `dbc script` using `s.RunPipeline` wrote `data/from-script/ids.csv`,
    and `s.Paths().FilesDir` was the configured directory.
  - `wait.file`, copied into `plugins_dir`, passed `dbc plugins --check`
    and found `drops/done.flag` relative to `files_dir`.

## Raised

- **N-199**: a script's own relative paths (`os.Create` in a script, a
  `go.action`, a `script.run` node) still resolve against the process's cwd.
  This is N-190's bug outside the file plugins. A `go.*` node can call
  `e.Path`, but a script has only `s`. The fix is an `s.Path(p)` reading
  `Paths.FilesDir`, plus docs.
