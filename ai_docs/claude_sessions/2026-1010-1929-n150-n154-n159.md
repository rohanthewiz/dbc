## N-150: refresh and DDL relist on a real Postgres

`TestLiveWorkspacePickSchema` gains three checks, after its pick of
dbc_live_wsb:

- **Refresh keeps the pick.** A table another client creates in wsb is
  listed after a Refresh. The listing stays on wsb, not public, and
  public's table is not listed.
- **A run's DDL relists by itself.** A `CREATE TABLE` run through the
  workspace relists on its own (`Relist`, `Relisted`), with the pick
  kept and the new table listed.
- **A Refresh mid-pick re-reads the pick.** A Refresh while a pick of
  dbc_live_wsa is still loading re-reads wsa, the user's latest pick
  (`refreshPickLocked` returns `w.schemaPick`). The pick's own load
  lands stale.

All pass on postgres:17, and the whole `./workspace` live suite stays
green. No defect found.

## N-159: rerunning a write asks first

New step "rerun a write asks first" (`rerunWriteConfirm`). It clicks the
tab's ↻, as the item's update suggested.

- **Setup.** It makes `e2e_rerun` on lite, waiting for the DDL's
  "relisted lite after the DDL" line, then runs an INSERT. It pins the
  INSERT's tab, so the count queries open tabs beside it rather than
  replacing it.
- **The confirm.** The ↻ opens "Run this statement again?" with the
  INSERT in its `<pre>`. **Keep the result** closes it, and no "rerun
  INSERT …" line appears in the log.
- **Run it again** reruns it ("rerun INSERT … completed"): the count goes
  from 1 to 2.

No defect found.

## Found on the way: `sidebar fold keys` fails on Chrome's ResizeObserver notice

The full web e2e suite failed in `sidebar fold keys` in about half of
the runs. The step itself passes; what fails is the harness's
JavaScript-error check, on "ResizeObserver loop completed with
undelivered notifications".

- **Not from this batch.** With few steps before it ("boot, sidebar
  fold") it fails every time, and it fails the same way at `d9e99c3`,
  the commit this session started from (checked in a scratch worktree).
  With the new steps before it, it passed four of four times, so the
  failure depends on what is on screen, not on the new steps.
- **Benign.** Chrome reports the notice as a window error when a
  ResizeObserver callback changes a size within the same frame; the
  notifications are delivered a frame later. The next batch raises it
  as N-201, for the harness to ignore that one message, and fixes it
  there.
