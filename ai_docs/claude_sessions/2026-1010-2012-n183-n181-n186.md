## N-183: stop a `dbc job run`'s run from another process

A run another process was running could not be stopped from dbc web's
Runs view, the TUI's run monitor, or `dbc run cancel`: none had a hold
on it.

- **Narrowed: only a signalable process is named.** A record names its
  process (`Run.PID`, `Host`) only when the engine is `Signalable`. That
  is the headless `dbc job run` / `dbc pipeline run` engine
  (`newHeadlessEngine`), whose interrupt stops exactly its runs. dbc
  web's and the TUI's interrupts would stop far more, so their records
  name nothing.
- **`Engine.Cancel`** sends SIGINT to a run another process is running,
  when the record names a process on this machine other than itself
  (`jobs/signal.go`). That process's own Ctrl+C handling cancels the
  run; it rolls back and ends canceled. Anything else is `ErrElsewhere`,
  as before.
- **Two safety notes.** A stale heartbeat makes a record read
  interrupted before any signal is sent, so a PID the system has reused
  is not signalled. Windows has no SIGINT, so there it refuses as
  before.
- **`dbc run cancel`** tries this first (`cancelLocal`: no dbc web and no
  secret needed), then dbc web's API. The follow-to-the-end loop is
  shared (`followCancel`).

## N-181: `dbc job run --wait=false`

- **In the calling shell:** the job is checked first, so a broken one
  fails there with its findings, exit 1. Then the run id is picked
  (`jobs.NewRunID`) and dbc runs itself again, detached (`detach.go`):
  - the same arguments, with `DBC_RUN_ID=<id>` set;
  - its own session: `Setsid` on unix, or a new process group with no
    console on Windows;
  - stdio to the null device; the record keeps the log.
- **The child** sees the variable and runs in the foreground under that
  id (`JobRequest.ID`; anything that is not a run id is refused). It is
  an ordinary signalable run, so N-183's cancel works on it.
- **The parent** waits for the record (at most 30 s), prints "started run
  ID (job NAME) — dbc run show ID · dbc run cancel ID" (or JSON with
  `-t json`), and releases the child. A child that exits without a
  record is reported, exit 1 ("run it with --wait to see why"); an
  unknown `-p` param is one such case, since only the engine checks
  params.
- **Scope.** Only `dbc job run` has the flag, as the item asked. Two
  detached runs of one job both start: overlap is checked per process,
  as for two cron runs.
- **Also fixed:** N-183 had left `dbc run cancel`'s help saying that a
  `dbc job run`'s run is stopped where it runs.

## N-186: a script job's preview rows

- **No origin tag; a direct hand-off instead.** `runForScript` has the
  script's session in hand, so the run gets `JobRequest.Show` =
  `s.Show`, which `runOne` calls in place of emitting a Preview event.
- **Every host at once:**
  - dbc web's and the TUI's script tabs get the rows with the script's
    other shows.
  - Headless `dbc script`, whose private engine dropped Preview events,
    now writes them out.
