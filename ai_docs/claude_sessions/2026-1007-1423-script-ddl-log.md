# Scripts always log their DDL

Session: `9b122688-3af7-4d8f-baa0-58d482f2618d`

## Ask

From the cats-todo backlog: "When running a script always log any DDL
statements". Then "/sw" (sess-wrap).

## Decisions

No questions were asked. Judgement calls:

- **"Log" means the script's log.** That is the same sink as `s.Print`: the
  connection's log in the TUI and dbc web, and stdout (text) or stderr
  (machine formats) headless. The line is `DDL <conn>: <statement>`,
  modeled on the `NOTICE: …` lines already there.
- **Logged before the statement runs**, as Postgres's
  `log_statement = 'ddl'` does. A long `CREATE INDEX`, or an `ALTER`
  waiting on a lock, is then in the log while it runs. A `Query`/`Exec`
  that fails adds `DDL <conn> failed: <err>`, since a script may ignore
  the error (a "drop if it exists" `_ =`). A failed `Copy`/`Writer` returns
  an error naming the statement, so it gets no extra line.
- **What counts as DDL**: CREATE, ALTER, DROP, RENAME, COMMENT, TRUNCATE,
  GRANT, REVOKE. That is the union of the engines' definitions: MySQL
  calls TRUNCATE DDL, and Postgres's `log_statement=ddl` logs GRANT and
  REVOKE. A wider net suits an audit log better. ATTACH/DETACH (SQLite)
  are left out.
- **Multi-statement Exec**: the text is split with `sqlsplit.Split`, and
  each DDL statement in it is logged, so a CREATE after an INSERT is not
  missed.
- **Verbatim statement text**, trimmed only. Both log panes already draw a
  multi-line entry (the TUI splits it into lines, dbc web uses
  `pre-wrap`).
- **Turned on in `script.run`**, the one path every script host goes
  through (headless, TUI, dbc web). It is not set per host, so a new host
  cannot forget it.
- **Copy and Writer are covered too.** A new `etl.Conn.Trace` hook is
  handed each statement a transfer runs to prepare a destination: Copy's
  CREATE TABLE (in the Writer's Setup, or on its own first for bytdb and
  MySQL), a Writer's Setup, and its TRUNCATE (or the DELETE standing in
  for one). `sdb.etlConn` points it at the same logger. Row traffic
  (SELECT, COPY, INSERT batches) is not traced.
- **`dbc copy` is left alone.** It runs through `sdb.S` but is not a
  script, and its terminal-only stderr carries a progress meter that
  `TestRunCopy` pins as empty. It never calls `LogDDL`. Raised as N-151.
- **`LogDDL` is one-way.** There is no off switch, so a script cannot opt
  out. It is listed in `sdbapi.hostOnly`, so Monaco completion does not
  offer it. `api.json` is unchanged.
- **Known gaps, documented**:
  - Statements run through the raw `s.DB` handle are not logged.
  - DDL inside a function body or a `DO` block is not seen, because the
    check is lexical on the first keyword.
  - On SQLite and MySQL a `Truncate` runs as a `DELETE`, which is DML and
    so not logged.

## What changed

- **`sqlsplit/sqlsplit.go`**: `IsDDL(stmt)` checks the leading keyword
  against `ddlVerbs`, with a comment table on where the engines disagree.
- **`sdb/sdb.go`**:
  - New `ddl` field and `LogDDL()` method.
  - `logDDL(conn, stmt) bool` splits the text, prints each DDL statement,
    and reports whether it printed any.
  - `run` (Query/Exec) logs before the statement runs, and adds the
    failure line after notices.
- **`sdb/etl.go`**: `etlConn` sets `Trace` to `logDDL` for that connection.
- **`etl/engine.go`**: `Conn.Trace func(stmt string)` and a nil-safe
  `trace`.
- **`etl/copy.go`**: `prepareDest` traces the CREATE when it runs it on its
  own (bytdb, MySQL).
- **`etl/writer.go`**: the setup loops in `newPGCopy` and `newInserter`
  trace each statement.
- **`script/engine.go`**: `run` calls `s.LogDDL()` before `fn(s)`.
- **`sdb/sdbapi/sdbapi.go`**: `LogDDL` added to `hostOnly`.
- **Tests**:
  - `sqlsplit.TestIsDDL`: comment-led DDL, DDL words later in a
    statement, a `DO` block.
  - `etl.TestCopyTracesSetup`: both of Create's paths (bytdb on its own,
    SQLite in Setup), each followed by the engine's truncate, and nothing
    traced on the source.
  - `script.TestScriptLogsDDL`: Exec and Query, a two-statement Exec, a
    failing DROP the script ignores, and that a session outside
    `script.Run` logs nothing.
  - `script.TestScriptETL` now expects the Copy's CREATE and the Writer's
    Setup CREATE among its printed lines.
- **Docs**:
  - README: a new "The DDL log" subsection under "The `sdb.S` API".
  - The dbc skill's `scripting.md`: a paragraph after `sdb.Result`.

## Verification

- `go build ./...`, `go vet ./...` and `gofmt` are clean.
- `go test ./...` passes: 24 packages, `CATS_*` stripped.
- `go generate` in `sdb/sdbapi` leaves `api.json` unchanged.
- A fresh binary was run headless on a scratch SQLite file with a script
  that does CREATE (multi-line), INSERT, a failing DROP it ignores, a
  Copy with Create, then a DROP:
  - In text mode the DDL lines interleave with the result block on
    stdout.
  - With `-t json`, stdout is just the JSON array, and the DDL and
    `failed` lines are on stderr.
- **Not run**: the TUI and web e2e suites. Both UIs reach the log through
  `script.Run` → `ScriptPrint`, the path `s.Print` already takes.
