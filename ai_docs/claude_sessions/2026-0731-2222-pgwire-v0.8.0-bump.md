# pgwire bumped to bytdb v0.8.0, tagged and pushed

Session: 38fd89eb-fc31-4688-b487-6d4ff6516a0f

Follows directly from [the previous session](2026-0731-2200-dbc.md), which
released bytdb v0.8.0 with the new `stdlib` package. That left the sibling
`pgwire` module still requiring v0.7.0.

## The change

One line, `pgwire/go.mod`: `github.com/rohanthewiz/bytdb v0.7.0` → `v0.8.0`.

`go mod tidy` touched nothing else, and `go.sum` needed no new entry — the
module carries `replace github.com/rohanthewiz/bytdb => ../`, so the dependency
resolves locally and never gets a hash. That is why the version line is mostly a
signal to external consumers rather than something the local build reads.

`btypedb` stays at **v0.7.0**: still its newest tag. The working checkout at
`~/projs/go/btypedb` is 3 commits past it (`3692710`, the OCC Stage 3 work), but
untagged, so there is nothing newer to point at.

Verified: `go build ./...`, `go vet ./...`, `go test -count=1 ./...` (pass,
4.8s), and `go list -m github.com/rohanthewiz/bytdb@v0.8.0` resolves from the
proxy — so consumers outside the workspace can actually fetch it.

## Repo state was clean going in

Asked explicitly before committing. `pgwire` is not its own repo — it is a
nested module inside `bytdb`, so its origin is bytdb's. At session start `main`
sat at `3d64020`, exactly even with `origin/main` (confirmed both against the
stored ref and after a fresh `git fetch`), working tree clean, and the `v0.8.0`
tag already on the remote pointing at that same commit.

## Tagging

The fetch surfaced that pgwire carries **its own module tags** —
`refs/tags/pgwire/v0.7.0` → `bf5cc31`, the previous bump commit. Nothing had
tagged pgwire since, so the new commit got `pgwire/v0.8.0` to match.

Final state, pushed to origin:

- `14c166f` — `pgwire: bump bytdb to v0.8.0`
- `pgwire/v0.8.0` — annotated tag on it
- root `v0.8.0` still on `3d64020`, untouched — only the pgwire module moved

## The author-email detour

The first commit (`923ec97`) went in as the work address, because that is what
global `user.email` holds. The repo's history is mostly the personal gmail
address — the three commits before `3d64020` all used it. Flagged before
pushing; the user chose to amend.

Amended with both `--author` and `GIT_COMMITTER_*` env overrides, since
`--author` alone leaves the committer wrong. The tag then had to be **deleted
and re-created**: it still pointed at the pre-amend hash `923ec97`, which the
amend had orphaned. Nothing had been pushed yet, so no history rewrite was
visible to anyone.

Then set `user.name`/`user.email` repo-locally in all three checkouts —
`bytdb`, `btypedb`, `dbc` — so the next commit does not repeat it. Global config
left alone.

- **btypedb** was already all-gmail in its history; this just pins it.
- **dbc** is the opposite: `fdc6e1d`, `9dbeada`, `5e9be86` were all authored
  with the work address. Future commits here will be gmail, so there is a
  visible identity switch at that boundary. Those are pushed; left as-is,
  since rewriting published history over an email is not worth it.

## Notes for next time

- **`pgwire`'s bytdb version is cosmetic locally.** The `replace` means the
  build always uses `../`. Bumping it is about the published module, so the
  thing worth verifying is that the version resolves from the proxy — not that
  the local build passes, which it would either way.
- **Amending a tagged commit orphans the tag.** `git tag -d` + re-create is the
  fix; check `git rev-list -n1 <tag>` afterward rather than trusting it moved.
- **Two module tag namespaces in one repo.** `vX.Y.Z` is the root module,
  `pgwire/vX.Y.Z` is the nested one. They version independently and a root
  release does not imply a pgwire one.
