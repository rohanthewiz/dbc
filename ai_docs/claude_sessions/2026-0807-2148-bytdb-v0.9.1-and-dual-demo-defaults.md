# bytdb bumped to v0.9.1, and the built-in demo now runs on both embedded engines

Session: 3110bbef-7949-44b8-b1d7-1de10c03ccb9

Three pieces of work, in order: a dependency bump, a `.gitignore` housekeeping
fix, then the substantive one — dbc's no-config startup now brings up a demo
connection per embedded engine, with bytdb active by default.

## 1. bytdb v0.8.0 → v0.9.1

`git ls-remote --tags` showed v0.9.1 as the newest plain tag (the repo also
carries `pgwire/v*` tags for its nested module — those are a different module
and not what dbc depends on). dbc has no `pgwire` requirement, so the bump was
the one line in `go.mod` plus `go.sum`.

`go mod tidy`, `go build ./...`, `go vet ./...`, `go test ./...` — all clean, no
API changes to absorb. Committed as `727f642`.

## 2. .gitignore for `.cats-todo/`

`.cats-todo/todos.json` was tracked and permanently dirty. Adding the ignore
rule alone would have done nothing — git ignores only untracked paths — so it
also needed `git rm -r --cached .cats-todo/`, which drops it from the index and
leaves the working copy alone. Committed as `698d7ac`.

## 3. Both embedded engines as the built-in default

The ask: "the option to use bytdb instead of SQLite as the default DB, or heck,
enable both as defaults."

"Default DB" here means the no-config fallback. dbc has always started, when it
finds no `dbc.toml` anywhere, on one in-memory SQLite connection named `demo`
seeded with a `cats` table. That is what changed.

### Decisions taken to the user

Two forks genuinely changed the work, so they were asked rather than assumed:

- **Which demo is active** — chose *both registered, bytdb active*. A bare `dbc`
  now opens on `demo-bytdb`; `demo` is still in the connection list.
- **Where the bytdb file lives** — chose the OS cache dir. bytdb has no
  in-memory mode (confirmed in `stdlib/stdlib.go` in the module cache: "bytdb
  has no in-memory mode, so a path is always a real file"), so unlike the SQLite
  demo it needs a real file somewhere. The cache dir is disposable in the OS's
  eyes, stays out of the user's cwd, and persists across runs.

### The seed-script problem

Worth recording, because it is the kind of thing that only surfaces when you
actually run it. The existing seed had:

```sql
adopted BOOLEAN NOT NULL DEFAULT 0
INSERT ... VALUES (1, 'Whiskers', 'Tabby', 3, 1)
```

On bytdb the DDL is accepted but the INSERT fails with `value does not fit
column type` — bytdb types booleans the way Postgres does and will not take an
integer in a boolean column. Probed this with a throwaway test in `db/` rather
than guessing.

The fix is one seed script for every engine, using the `true`/`false` keywords.
SQLite has accepted those since 3.23 and still *stores* them as 1/0, so the
SQLite demo renders exactly as it always did and `scripts/export_report.go`
(which does `WHERE adopted = ?` with `1`) is untouched. bytdb renders
`true`/`false`. Same rows, same script, both engines.

### What was written

- **`config/config.go`** — the no-config branch became `demoFallback(demo)`,
  building both connections with the active one first (several call sites treat
  `Connections[0]` as the stand-in when a default cannot be resolved).
  `LoadDemo(path, engine)` carries the choice; `Load` delegates to it with the
  default, so no existing caller changed. `DemoBytdbPath()` resolves
  `os.UserCacheDir()/dbc/demo.bytdb`, falling back to the temp dir where the
  cache dir is undefined, and creates the parent — the driver creates the file
  but not the directory. `ParseDemoEngine` rejects unknown values rather than
  silently falling back, since a silent fallback leaves the user staring at the
  engine they just asked not to use.

- **`main.go`** — `-demo bytdb|sqlite`, defaulting from `$DBC_DEMO`. Only
  meaningful with no config file; a real config names its own
  `default_connection`.

- **`db/demo.go`** — seed statements hoisted to a package var, plus `SeedDemos`,
  which seeds every demo connection and *prunes* the ones that fail instead of
  aborting the launch. This matters more than it did before: the bytdb demo is a
  file, so it has failure modes the in-memory SQLite one never had — another dbc
  already holds the engine, an unwritable cache dir, a leftover file from an
  incompatible version. A pruned connection is dropped from the config (leaving
  it listed would only offer a connection that errors on every query), a warning
  is recorded, and the default moves to whatever survived. Only if *nothing*
  seeds does the launch fail. The `DELETE FROM cats` in the seed also stopped
  being decorative — the bytdb demo outlives the process, so a second launch
  would otherwise collide with the first launch's rows.

- **`db/manager.go`** — `Manager.Drop(name)`, so a connection known to be
  unusable is closed and forgotten rather than handed to the next caller.

- **`ui/app.go`** — the startup log names every demo that survived seeding and
  marks the active one. The point of shipping two is that the user knows the
  second is there.

- **README.md, dbc.example.toml** — a table of the two demos, the `-demo` flag,
  and a note that the flag goes quiet once a config file exists.

### Tests

`config/demo_test.go` and `db/demo_test.go`, new. An `isolateDemo` helper
`t.Chdir`s somewhere with no `dbc.toml` and repoints `$HOME` (and clears
`$XDG_CACHE_HOME`) so the loader is forced down the no-config path and the demo
file lands in a temp dir instead of the real cache dir.

Covered: both engines registered with bytdb first and active; `-demo sqlite`
flips the order and default without dropping the other; the demo path is
absolute and under `dbc/` in the cache dir; a config file overrides `-demo`
entirely; `ParseDemoEngine` cases; the seed loads identically on both engines
(8 rows, same first row); seeding three times still leaves 8 rows; a broken demo
is pruned with a warning and the default moves; nothing seedable is a hard
failure.

Verified end to end by actually running it — `dbc "SELECT ..."` on bytdb
(`adopted` shows `true`/`false`), `-demo sqlite` (shows `1`/`0`), `-c demo`
while bytdb is active, and `-demo mysql` failing with a named error.
`gofmt`, `go vet`, and the full suite are clean.

## Notes for next time

- `scripts/export_report.go` and `testdata/show_two.go` hard-code the connection
  name `"demo"`. That is why the SQLite demo kept its old name and its old
  in-memory DSN rather than being renamed to something symmetrical like
  `demo-sqlite` — the rename would have quietly broken every shipped script.
- The demo file at `~/Library/Caches/dbc/demo.bytdb` is real and now exists on
  this machine. Deleting it is safe; it is re-seeded on the next launch.
- Every headless invocation seeds *both* demos, including runs that only touch
  one. Cheap, but it does mean a bare `dbc "SELECT 1"` opens the bytdb file. If
  that ever becomes a problem, seeding lazily on first use of a connection is
  the obvious next move.
