## What happened

### bytdb N-017 filed

bytdb's `pg_attribute` and `information_schema.columns` built rows from
`userDescs()` only, so views (in `pg_class` under synthetic `viewOID`s) had
no columns — true at bytdb HEAD then (v0.15.0), not just dbc's pinned
v0.9.1. Recorded on the Roadmap of `~/projs/go/bytdb/ai_docs/todo/next-list.md`
as N-017; dbc's N-026 closing line cross-referenced it.

### Checking the "done" report before acting on it

When bytdb reported N-017 done, both halves (view columns *and* views in
`information_schema.tables`) were still uncommitted in bytdb's working tree;
no tag had either. Dropping dbc's bytdb case while pinned to v0.9.1 would
have made views vanish from the sidebar. So the dbc change was prepared and
tested against bytdb's working tree through a **scratch `go.work`**
(`GOWORK=<scratchpad>/go.work`, `use` both repos), leaving dbc's `go.mod`
alone:

- dbc unchanged, against bytdb HEAD: full suite green — the v0.9.1 → HEAD
  jump broke nothing.
- With the change: green against HEAD; against v0.9.1 exactly the two view
  tests fail (`TestTablesQueryRunsOnBytdb`, `TestColumnsOnBytdb`), which is
  what makes them a guard against a downgrade.

The user had bytdb push and tag it (v0.16.0).

### Adopted (`946060e`)

- `go get github.com/rohanthewiz/bytdb@v0.16.0` (from v0.9.1), `go mod tidy`.
- `db.TablesQuery`: the bytdb-only `pg_class`/`relkind` query is gone;
  `case "pgx", bytdbdrv.DriverName:` shares the Postgres
  `information_schema.tables` query.
- `TestColumnsOnBytdb` now also asserts a view reports its columns; the
  per-driver test expects `information_schema.tables` for bytdb.
- `go vet` clean; `go test -race -count=1 ./...` green on the real module.
- N-026's closing line in the next list updated: bytdb views have columns
  from v0.16.0.

## Gotchas worth remembering

- A sibling session's "done" can mean done in its working tree. Check for a
  tag before changing code that depends on it; a scratch `go.work` via
  `GOWORK=` tests against the unreleased tree without touching `go.mod`.
- `go install …@latest` refuses modules with `replace` directives, so a
  `replace` is never the way to ship against an unreleased sibling.
