# N-270: migrations take a lock per database; MySQL says what a failure kept

Session: `acbda969-9a04-4496-9a85-1c6665f58eaa`

## Ask

"Do Next list item N-270" (RPU plan, phase 2), then `/sw`. The item:
`migrate/` takes no runner lock, so two deploys both read `applied` and
both run a data migration, and the version table has no unique key to
stop the second row. And on MySQL, `runOne` "rolls back" DDL that MySQL
committed as it ran: re-running `up` fails on statement 1 and the error
never says the migration was partly applied. Suggested fix:
`pg_advisory_lock` / `GET_LOCK` / `BEGIN IMMEDIATE` around a run, and on
MySQL report statement k of n as applied.

Commit: `1d691f3`.

## Premises, checked first

- **Callers.** Only `migrate.go` (the CLI) uses the package: `NewWith`,
  then one public method per verb. So the lock could sit inside the
  public methods without touching the CLI.
- **goose's Postgres lock key.** goose's `DefaultLockID` is documented as
  the CRC-64/ECMA of "goose"; computed it: `5887940537704921958`. Using
  the same key makes a goose run (with its session locker) and a dbc run
  exclude each other on a shared database while a project switches tools.
- **bytdb needs nothing.** bytdb's `Open` takes an OS lock on the file
  (`btypedb.AcquireLock`, flock), so a second process cannot open the
  database at all, and one CLI process runs one migrator.
- **MySQL's implicit commit, run on mysql:8.4** before writing the rule
  (plain `mysql` client, `--force`):

  | Inside `START TRANSACTION` … `ROLLBACK` | What stayed |
  | --- | --- |
  | `INSERT 1; CREATE TABLE t2; INSERT 2` | 1 and 2 — the DDL committed 1, and the session is then in autocommit, so 2 committed on its own |
  | `INSERT 3; CREATE TABLE t2` (exists, error 1050) | 3 — the commit happens before the DDL runs, failure or not |
  | `INSERT 4; CREATE TABLE t3 (id int,` (syntax, 1064) | nothing — the parse fails before the commit |
  | `INSERT 5; CREATE TEMPORARY TABLE tt` | nothing — TEMPORARY does not commit |
  | `INSERT 6; ALTER TABLE t1 ADD COLUMN id` (dup column, 1060) | 6 |

  The item's "report statement k of n" undersold the autocommit half:
  once any statement before the failure is DDL, *every* statement before
  the failure stays, DML included.

## Design

### One held connection, a lock per engine (`migrate/lock.go`)

Every writing command (`up`, `up-by-one`, `up-to`, `down`, `down-to`,
`redo`) runs inside `Migrator.locked`: it reserves one `*sql.Conn`, takes
the dialect's session lock on it, runs everything — version-table read
included — through that connection, and releases. `redo` holds it once
across its down and its up. `status` and `version` take no lock (they
show a run's progress, which is what they're asked for). Session locks
belong to a session, hence the pinned connection; it also avoids a pool
capped at one connection deadlocking between a lock connection and a
work connection.

| Engine | Lock | Held |
| --- | --- | --- |
| Postgres | `pg_try_advisory_lock(5887940537704921958)` | whole run |
| MySQL | `GET_LOCK(LEFT(CONCAT('goose_db_version:', IFNULL(DATABASE(),'')), 64), 0)` — names are server-wide, so the database is in the name; 64 chars is GET_LOCK's limit | whole run |
| SQLite | `BEGIN IMMEDIATE` per migration + re-read of its version row | each migration |
| bytdb | none | — |

**Polled, not waited on.** Both session locks are tried every
`lockPoll` (1 s) with a zero wait, not taken with a blocking
`pg_advisory_lock` / `GET_LOCK(…, -1)`. On Postgres this is required: a
waiter blocked inside `SELECT pg_advisory_lock(…)` is a running
statement holding a snapshot, and a `CREATE INDEX CONCURRENTLY` in the
holder's run waits for every older snapshot — each waits for the other.
Reproduced (below): with the blocking wait swapped in, Postgres reported
`deadlock detected (40P01)`. goose's locker polls for the same reason. On
MySQL polling keeps every statement short and the wait in Go, where ctx
ends it cleanly (a wait inside GET_LOCK can only be abandoned by closing
the connection).

The first miss logs who holds it: `waiting for the migration lock:
another run holds it (pid 164)` — Postgres reads `pg_locks` (a bigint key
is split: `classid` the high 32 bits, `objid` the low, `objsubid = 1`),
MySQL `IS_USED_LOCK` (a connection id). Then `migration lock taken`.

Release runs on a fresh 5 s context (ctx may be what ended the run); if
it fails, the connection is discarded rather than pooled
(`c.Raw(func(any) error { return driver.ErrBadConn })`), since the server
frees a session's locks when the session ends.

A transaction-mode pooler (PgBouncer `pool_mode=transaction`) cannot hold
a session lock — noted in the code and README.

### SQLite: per migration (`runImmediate`)

SQLite has no lock that outlives a transaction, so wrapping the whole run
(the item's wording) would put every migration in one transaction:
`NO TRANSACTION` migrations could not run, and "earlier ones stay
committed" would change. Instead each transactional migration is driven
by hand on the held connection: `BEGIN IMMEDIATE` (the write lock before
the first statement; a plain BEGIN takes it at the first write, after the
re-read), `stillToDo` re-reads the newest version row, and a migration
another run already did is skipped (`SKIP 20_bump.sql (another run
applied it)`, or "rolled back" for a down). `runOne` now returns `ran`, so
skipped ones are not in `done`. database/sql's `BeginTx` cannot ask for
IMMEDIATE (modernc takes it only from the DSN), hence the manual
BEGIN/COMMIT; a failed ROLLBACK discards the connection. A
`NO TRANSACTION` migration on SQLite re-reads just before it runs —
narrower window, not closed. The manager's `busy_timeout(5000)` is what
makes a second runner wait at `BEGIN IMMEDIATE` instead of failing.

`ensureTable` also had a race (two runners both probing "no table"):
a CREATE that fails now re-probes, and a table that is there is success.

### MySQL partly applied (`migrate/commit.go`)

`Dialect.commits` (set for MySQL only: `mysqlCommits`) classifies a
statement by its leading verb via `sqlsplit.MySQL.Verbs`: alter, create,
drop, rename, truncate, grant, revoke, install, uninstall, begin, start,
lock, unlock, analyze, cache, check, flush, optimize, repair, reset —
except `CREATE/DROP TEMPORARY`. Left out on purpose: `set` (mostly
session variables), `load` (LOAD DATA commits only on NDB), replication
control. Lexical: a CALL whose procedure runs DDL is not seen.

`keptAfterFailure(stmts, i, err)`: if any statement before i commits →
i; else if statement i commits and the error is not a syntax error
(`*mysql.MySQLError` 1064 or 1149) → i; else 0. i is `len(stmts)` when the
version row fails. The error gains a `partly_applied` field and the log a
plain line, since the CLI's error arrives as a structured log line:

```
PARTIAL 10_bad.sql: statements 1-2 of 3 stay applied (MySQL commits DDL as it runs, so the rollback could not undo them); the version table still lists the migration as pending, so undo or finish them by hand before migrating up again
```

A failing `NO TRANSACTION` migration (or bytdb, which has no transactional
DDL) reports the same on any engine, with its own reason.

Kept as it was: no unique key on `goose_db_version` — goose's history is a
log (older goose wrote a rollback as an `is_applied = false` row), so a
key on `version_id` would break reading a goose database.

Two small things hit while writing: `MySQL`'s initializer naming
`mysqlCommits`, which read `MySQL.split`, is an initialization cycle Go
refuses — it uses `sqlsplit.MySQL` directly. And the internal methods
(`upTo`, `down`, `downFrom`, `runOne`) take the held `*sql.Conn`, while
`applied`/`ensureTable` take a `querier` (`*sql.DB` or `*sql.Conn`).

## Tests

`migrate/lock_test.go` (unit, no server):

- `TestSQLiteSkipsWhatAnotherRunDid` — the race made deterministic: a
  runner reads the table, another applies, the first runs 20 from its
  stale reading and skips; same for down; its connection is not left
  holding the write lock.
- `TestSQLiteConcurrentRunsApplyOnce` — 8 runners, each its own handle on
  one file, `fresh=true` (also racing to create the version table) and
  `fresh=false`. **Both fail on the old `run.go`** (checked by restoring
  it: "table goose_db_version already exists", and with the table
  pre-created "table counter already exists").
- `TestSQLiteFailedMigrationFreesTheLock`.
- A fake `sessionLock` on the SQLite dialect: wait/log/release and that
  status/version take no lock and redo takes one
  (`TestSessionLockWaitsAndReleases`), ctx ending the wait with the
  context's error (`…WaitEndsWithContext`, which the CLI turns into
  "canceled"), a failed release discarding the connection
  (`…ReleaseFailureDiscardsConn`).
- `TestMySQLCommits`, `TestKeptAfterFailure`, `TestNoTxFailureSaysWhatStayed`.

`migrate/live_test.go` (opt-in, `DBC_LIVE_PG_DSN` / `DBC_LIVE_MYSQL_DSN`;
drops `goose_db_version` in the DSN's database):

- `TestLiveConcurrentRunsApplyOnce` — 6 runners per engine, a slow data
  migration: one row, one version row each, a waiter named the holder.
- `TestLiveLockWaitsForHolder` — the lock taken by hand from another
  session (on Postgres by goose's key): the run waits, names that pid /
  connection id exactly, ends with its deadline, then runs once released,
  and releases.
- `TestLivePostgresConcurrentIndexWhileWaiting` — migration 10 writes and
  sleeps, 20 is `NO TRANSACTION` `CREATE INDEX CONCURRENTLY`, a second
  run starts waiting during 10. Both finish. Proven meaningful with a
  throwaway test (deleted) that swapped in the blocking wait: the second
  run failed with `deadlock detected (SQLSTATE 40P01)`.
- `TestLivePartlyApplied` — four failing migrations on both engines; the
  report is checked against whether the migration's row actually stayed
  (Postgres always 0 kept).

Runs: `go test -count=3 ./migrate`; live suite on postgres:17 and
mysql:8.4 green first time; `go test -race -count=3 ./migrate` with both
DSNs, `go vet ./...` and `go test ./...` green.

Real binary (scratch dir, CATS_* unset): two `dbc --driver postgres
--dsn … --dir migs migrate up` 0.3 s apart — one printed `waiting for the
migration lock: another run holds it (pid 164)`, `migration lock taken`,
`no migrations to run. current version: 20`; the other applied both; the
seed table held one row and each version one row. A failing MySQL
migration printed the PARTIAL line and the `partly_applied` field, exit 1;
`migrate status` showed it pending; its table and row stayed, as reported.
(Setting `HOME` to the scratch dir for dbc also hid docker's config from
the docker CLI in the same script — the checks were rerun outside it.)
