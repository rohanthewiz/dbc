## N-192 and N-176: sql fields complete, table fields offer, by the node's conn

A pipeline tab is on no connection, so its inspector's sql fields had no
completion and its table fields were plain lines.

- **A cache keyed by connection name: `workspace.ConnCompletions`.** It
  reads with the workspace's rules: `readCompletions` and `readRoutines`
  were lifted out of `Workspace` into package functions both share.
  - A catalog too big to read whole is read scoped, and remembered as
    such.
  - A failed read is remembered for `complRetry`.
  - The routines are read beside the schema.

  One thing differs: nothing runs through this cache, so instead of a
  workspace's drop-on-DDL, an entry is read again after `ConnComplTTL`
  (a minute). Editing or deleting a connection drops every entry.
- **Two routes.** The connection name goes in the body or the query,
  because a `<conn>/<database>` name holds a slash.
  - `POST /api/v1/conn-complete {conn, buffer, caret}` answers in a
    statement editor's shape (`completeAnswer`, now shared with
    `handleComplete`).
  - `GET /api/v1/conn-tables?conn=` lists each table's sidebar label,
    tables then views. A failed read is a 200 with `error`, since nothing
    went wrong in dbc.
- **Decision for N-176.** The table list comes from the completion read,
  not the Manager's per-schema catalog read the item named: one read
  serves both fields, and a too-big catalog is read scoped for both.
- **The page:**
  - `editor.js` `minis` is now a WeakMap of each small editor's options.
    A SQL field passes `conn()`, which `pipelines.js` `connOf` answers at
    each ask, since the conn field can change under the editor.
  - A conn written as `${param}` gets nothing, since only a run resolves
    it.
  - The table field offers its node's connection's tables in a
    `<datalist>`; `tablesOf` keeps each answer 30 s, because the
    inspector is drawn again after every check.
  - F12 and F2 still skip these small editors.

## N-178: the assistant in a pipeline or job tab

The assistant read the tab's hidden editor, the spec's JSON, as SQL.

- **Decision: the pipeline as a pipeline**, as N-134 did for scripts,
  rather than leaving the editor out.
- **The page** sends the file (`pipeline` or `job`) and the run its
  canvas shows (`run`, through `dbc.cmd.lastRun`).
- **`workspace.PipelineChatContext`** marks the text as the spec and adds
  the connections by name and driver, and the tables its SQL names.
- **The run's error.** The server reads it from the jobs engine
  (`runErr`), only when the run's Source is this file: an id from
  elsewhere cannot put another run's error under the spec. Without an
  error, a preview's rows on screen go along.
- **The prompt.** `ai.Build` fences the spec as JSON, under a pipeline
  preamble that asks for JSON back. The plugins and the sdb API go on the
  conversation's first such question, as a script's do.
- **Found on the way.** "⤓ insert" on a SQL block in a pipeline or job
  tab inserted into the hidden JSON spec; it now refuses, with a hint to
  copy the SQL into a node's field.
