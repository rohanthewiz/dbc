# N-199: `s.Path` — a script's own relative paths resolve against `files_dir`

Session: `3970d5e7-7ce1-4548-ad0d-2b3bd33147a2`

## Ask

1. N-199 (from the cats-todo backlog): a script's own relative paths still
   resolve against the process's working directory. `os.Create("out.csv")`
   in a script, a `go.action` or a `script.run` node writes into the
   shell's directory from `dbc script`, and into wherever dbc web was
   started when a schedule runs it. That is N-190's bug, outside the file
   plugins. A `go.*` node can call `e.Path`, but a script has only `s`. Add
   `s.Path(p)` (`Paths.FilesDir`, as `Env.Path` does) and say in the
   scripting docs to open files through it.
2. `/sw n199-script-path`.

## Decisions

| Question | Choice | Why |
| --- | --- | --- |
| Where the rule lives | `pipeline.ResolvePath(filesDir, p)`, which `Env.Path` and `s.Path` both call | One rule, so a script and a file node cannot come to disagree on where `exports/orders.csv` is. `Env.filesDir` stays unexported; a plugin has no directory to pass, so it still has the one way (`e.Path`). |
| `s.Path`'s signature | `Path(p string) string` | It goes straight into an os call: `os.Create(s.Path("out.csv"))`. The only failure is a `~` path with no home directory. Then `p` comes back as written, and the open fails naming it. `Env.Path` keeps `(string, error)`. |
| `s.Export` | Also goes through `s.Path` (beyond the item) | It is dbc's own path-taker for scripts, as `csv.write` is for pipelines, and it had the same bug. The built-in `export_report` example and the `export` template wrote relative files through it. The template even said "relative to the directory dbc runs in; write an absolute one to be sure". The parallel is "dbc's writers apply files_dir; your `os.*` calls go through `s.Path`", as pipelines have "the built-ins apply it; your plugin calls `e.Path`". The cost is the shell, the trade N-190 made for `dbc pipeline run`: `dbc script` puts a relative export in files_dir (default `$HOME`), not the cwd. |
| Missing directories | `s.Export` makes them; `s.Path` makes none | Found in the real binary: with `files_dir = "data"` not yet created, `export_report` failed. The cwd always existed, and `export.ToFile` makes no directories. `csv.write` makes its file's directories, so `Export` now does too. `s.Path` only names a path; the docs say to `os.MkdirAll` first. |
| The sdb summary's 14 KB budget | Collapse field groups in the summary, not raise the budget | It had 46 bytes left; `s.Path` added ~150. `render` printed `Pipeline, Fragment, Node string`'s one doc three times, once per name. Merging a run of fields that share a type and a non-empty doc onto one line saved ~150 bytes, with nothing lost. Result: 14,293 bytes, 43 under. |

Not handled (raised as N-200): inside a `go.action` or `script.run` node,
`s` is the session that ran the pipeline, so `s.Path` uses that session's
`Paths.FilesDir`. A script that runs a pipeline with a different
`PipelineOpts.FilesDir` gets file nodes in that directory, but the node's
`s.Path`/`s.Export` stay on the host's. Every host's runs agree today.
`S` can't be cheaply copied with another directory (mutex, open
Readers/Writers).

## How it flows

```
config.FilesDir ─► sdb.Paths.FilesDir (main.go, workspace/run.go, jobs.Engine.paths)
                      │
script ──────────────┼─► s.Path(p) ──┐
s.Export(r, f, p) ───┘   (+ MkdirAll)│
go.action / script.run: e.S is the   ├─► pipeline.ResolvePath(filesDir, p)
  run's *sdb.S → the same s.Path     │      relative → Join(filesDir, p)
file node ─► e.Path(p) ──────────────┘      "~"/"~/…" → home · absolute → as is
                                            no filesDir → as written (cwd)
```

`dbc copy`'s session (`copycmd.go`) sets no Paths, but it runs no script.

## Changes

- **`pipeline/builtin_files.go`**: `ResolvePath(filesDir, p)` (exported,
  commented as being for sdb). The package-level `inFilesDir(dir, p)` holds
  the test, and `Env.inFilesDir` (which `pathErr` uses) wraps it.
  `Env.Path` calls `ResolvePath`, nil Env included.
- **`sdb/pipeline.go`**: `S.Path`, with a doc that covers the one-result
  choice, the no-files_dir case and the node case.
- **`sdb/sdb.go`**: `Export` resolves through `s.Path` and makes missing
  directories (`os`, `path/filepath` imported); its doc says so.
- **`sdb/sdbapi/summary.go`**: field groups on one line.
  **`summary_test.go`** checks the group line. **`api.json`** is
  regenerated.
- **`script/plugins.go`**: the `go.action` palette doc names `s.Path`.
- **`scripts/export_report.go`**, **`scripts/templates/export.go`**: print
  `s.Path(name)`, the real location. The comments say a relative path is in
  files_dir, and the template shows `os.Create(s.Path("notes.txt"))`. Their
  first sentences, which the browsers show as descriptions, are unchanged.
- **Docs**:
  - README: the config line, the `s.Export` and `s.Path` rows of the API
    table, a new `#### Files` subsection, and a sentence in the pipeline
    `files_dir` paragraph linking to it.
  - `.claude/skills/dbc/scripting.md`: the table rows, a **Files**
    paragraph, and `ResolvePath` in the pipelines bullet.
  - `SKILL.md`, `dbc.example.toml`, the `config/config.go` FilesDir doc,
    and the `config/files.go` header.

## Checks

- **New tests**:
  - `sdb/pipeline_test.go` `TestPath`: relative, nested, absolute, `~/`,
    `""`, and a bare session (no Paths).
  - `script/plugins_test.go` `TestScriptFilesDir`: files_dir starts missing.
    Through the interpreter, a script calls `s.Export` into
    `exports/fd-export.csv`, which creates files_dir and the subdirectory.
    It then writes its own file through `s.Path` and runs a pipeline with a
    `go.action` (a wrapped snippet) and a `script.run` of a saved script,
    each writing through `s.Path`. All four files are in files_dir, none in
    the cwd, and the printed `s.Path` is absolute.
  - The test fails with `Export`'s `s.Path` line disabled (the export lands
    in the cwd) and, separately, with its `MkdirAll` disabled.
  - `TestTemplatesRun` is unchanged and still passes: its bare session has
    no files_dir, so the template writes in its temp cwd.
- **Full suite**: `go vet ./...` and `go test ./...` green, `gofmt -l`
  clean.
- **Real binary** (built to the scratchpad), with a temp config
  (`files_dir = "data"`, `scripts_dir`, a scratch SQLite `demo-sqlite`
  seeded with `cats`) and run from a sibling empty directory:
  - `dbc script own`: an `s.Path` file in `own/`, plus an export. Both
    landed under `cfg/data`; `s.Path("/tmp/x")` stayed `/tmp/x`, and
    `~/y` went to `$HOME/y`.
  - `dbc script export_report` (the built-in example), with no `data/` yet:
    four files in `cfg/data`, each printed with its full path. Before the
    mkdir fix this failed with `no such file or directory`.
  - `dbc pipeline run node.json` (`go.action` writing `from-action.txt`,
    `script.run` of `own`): succeeded, all under `cfg/data`.
  - The cwd stayed empty throughout.
