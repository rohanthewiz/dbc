## N-198: job findings placed by the job's own step ids

N-195, N-196 and N-197 fixed pipelines. Jobs still cut a where at its
first dot in all four places: `jobs.js` `diagsAt`, the inspector's
label, `lineOf` and `jobs.Locate`.

- **Match against the spec, as pipelines now do.** `jobs.stepAt` reads
  `pipelines[i]` as the i-th step. Otherwise it takes the longest step
  id that is the whole where, or is followed by a dot and a step key
  (`after`, `params`, `params.<p>`). Requiring a step key after the dot
  keeps `triggers.tz` the job's even beside a step called `triggers`.
- **Find the step inside the list.** The step's `"id"` is now looked for
  inside `"pipelines": [`, so a job named like a step, or a param doc
  holding the name, no longer takes the step's findings. The id is
  decoded through `pipeline.FindName` (the closure `pipeline.Locate`
  used, now exported with `IndexIn`). A duplicate id is found as itself.
- **A param name may hold dots.** So `params.a.b` is two keys, not three
  (`keysOf`).
- **CheckJob names an invalid step by its place in every finding.**
  Before, only the "not a step id" finding used `pipelines[i]`; its
  `after` and `params` findings used the invalid id, which can be "".
  Now all of them do, as `pipeline.Check` names a node.
- **The server places job findings.** `job-check` returns each finding's
  line and column (`jobs.Locate`; a parse error by `ParseErrorAt`), as
  `pipeline-check` does. `jobs.js` drops `lineOf`. `diagsAt` matches as
  `stepAt` does and gives each finding a `label` (what follows the
  step), which `drawDiags` prints.

## N-193: F12, Shift+F12 and F2 in a pipeline go field

The Go providers in `scripts.js` are registered for every Go model, so
they already fired in the inspector's go fields. The server parsed the
snippet as a file, found no package clause, and answered nothing.

- **Fixed in the script package, not the handlers.** `checkText` wraps
  text with no package clause through `WrapSnippet`, the way the node
  runs it. It keeps the header's byte length (`len(src)-len(code)`) and
  line count on `checked`. `Resolve` and `Rename` move the caret in and
  the spans, Def and edits out. The web handlers are unchanged and still
  convert to UTF-16.
- **What the header declares is not in the editor.** An implied import
  gets no Def (as a builtin has none), its header span is dropped from
  the uses, and F2 refuses it. Rename's sentences name the field's own
  lines, and an import the header holds reads "the name of a package the
  snippet uses".
- **Entry points are not renamed.** `snippetEntries` (beside
  `bindPlugin`) lists every name a go.* node calls: Next, Open, Close,
  Apply, Flush, Write, Commit, Abort, Run.
- **Found on the way: plugin files.** A ◈ plugin file has a package
  clause, so it was never wrapped. F2 would rename its `Apply` or its
  `Plugin` var, and the plugin would stop loading, since dbc looks both
  up by name. A file that declares a package-level `var Plugin` now
  refuses both.

## N-182: one JSON document per run

`dbc pipeline run -t json` wrote the preview results, then the stats:
two documents.

- **The results go inside the document.** They sit under `"results"`,
  in the shape `dbc script -t json` writes them, the same as the `-o`
  file. I did not send them to stderr: they would be mixed with the log.
  The stats keys are unchanged, so `jq .status` still works.
- **The premise was narrower than the bug.**
  - A real run whose pipeline ends in a preview sink (`cats-report`)
    did the same, not only `--preview`.
  - With `-o`, stdout was not the stats alone, as the list's last
    update said. The log (`scriptLog` sends it to stdout when `-o` is
    set) and `writeOut`'s "wrote N rows to F" came first.
- **The fix.** Under `-t json`, `newRunOutput` sends the log to stderr.
  `runJSONResults` either embeds the results or writes the `-o` file
  with its note on stderr (`writeOutTo`, which `writeOut` now calls).
- **`dbc job run -t json` had the same bug** with its record, and gets
  the same fix.
