- **N-187**: `userdata/runs.go` gets `heads`, an in-process cache of record
  heads, keyed by directory and then file name. `readHeads` reuses a head
  while its file is unchanged: `os.SameFile`, size and mtime.
  `writeAtomic` renames a new file in on every write, so a rewrite is
  always a new inode. `forget` drops the heads of pruned or removed records
  on each directory read. `readHead` is split into stat + `parseHead`; the
  stat now comes before the read, so a race costs only a re-parse, never a
  stale head.
  - Neither proposed fix was taken. A Limit can't stop reads early: the
    listing keeps the newest by Started, and an id's local wall-clock
    second can be out of order across a DST fall-back or a zone change.
    Reading only a file's leading bytes would need Rows (summed over every
    fragment) written into the header.
  - The long-lived listers gain: the TUI Runs list and dbc web's Runs view
    re-list every 2s while a run is live. A one-shot `dbc runs` still
    parses everything once.
  - Measured with a throwaway test (deleted afterwards): 4,000 records
    with logs (20 names × 200), a Limit-200 listing took 482 ms cold and
    about 13 ms cached.
  - The `RunsStamp` doc and the TUI tick comment (`tui/runs.go`) were
    updated to the new cost.
  - Test: `userdata.TestRunHeadsCache`. It checks that a same-size rewrite
    through SaveRun is re-read, that an in-place change keeping the same
    file, size and mtime is served from the cache (so the hit path is
    really exercised), and that a pruned record leaves the cache.
