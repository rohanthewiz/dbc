# N-289: CALL, EXECUTE and FETCH show their rows; a procedure's every result set

Session: `ae3a42e5-1257-4542-8159-d2f52feca192`

## Ask

"Next list item N-289": statements outside `queryVerbs` ran as an Exec and
lost their rows — `CALL`, `FETCH`, `EXECUTE`, MySQL
`CHECK`/`ANALYZE`/`OPTIMIZE TABLE` — and `NextResultSet` was never used, so
a procedure's further results could not show. The item's fix: for a verb
that is neither clearly a read nor a write, run as a Query and fall back to
the affected count when no columns come back. Then `/sw`.

## The premise, checked first

A throwaway probe (database/sql straight onto pgx and go-sql-driver) against
postgres:17 and mysql:8.4, before any product code:

| Statement | As Exec (what dbc did) | As Query |
| --- | --- | --- |
| MySQL `CALL` of a procedure with two SELECTs | affected 0 | two result sets through `NextResultSet` |
| MySQL `CALL` of a procedure that only UPDATEs | affected 3 | no columns; `SELECT ROW_COUNT()` then says 3 |
| MySQL `CHECK`/`ANALYZE`/`OPTIMIZE`/`CHECKSUM TABLE`, `HANDLER … READ` | affected 0 | rows |
| Postgres `FETCH 2 FROM c` | affected 2 | 2 rows |
| Postgres `EXECUTE` of a prepared INSERT | affected 2 | no columns; command tag `INSERT 0 2` |
| Postgres `CALL p(21)` with an INOUT parameter | affected 0 | one row |

Two things the item did not say came out of it:

- **A Query loses the count.** `sql.Rows` has no rows-affected, so "fall
  back to affected when `Columns()` is empty" needs the count from
  somewhere else, or `EXECUTE ins` and a writing `CALL` regress to "0
  affected".
- **pgx's cached mode is unsafe for these statements.** In the pool's
  default mode pgx prepares each distinct text once and reuses the columns
  it described. For `FETCH 2 FROM c` the columns are those of whatever `c`
  is now, and the server checks nothing: with the cursor declared again
  over another query the rows came back under the first one's columns
  (`convert field 0 failed: invalid length for int4: 2`).

One part of the item was wrong: `(SELECT 1) UNION (SELECT 2)` was not
affected. `sqlsplit.Verbs` reads through the paren, so it was already a
Query.

## What changed

**Three kinds of statement (`db/stmtkind.go`)**

```
             ┌─ isQuery ───────────────► kindRows   Query, rows
statement ───┼─ execVerbs ─────────────► kindExec   Exec, rows affected
             └─ anything else ─────────► kindMaybe  Query ─┬─ columns ──► rows
                (Postgres, MySQL)                          └─ none ─────► rows affected
```

- `execVerbs` lists the verbs that return no rows on any engine: the
  writes, DDL, transaction control, session state, access and admin. A verb
  that any engine answers with rows is left out (`ANALYZE` is rowless on
  Postgres, a result set on MySQL).
- `kindMaybe` is everything not known to be an Exec, rather than a list of
  row-returning verbs: a verb missing from `execVerbs` costs a round trip,
  where one missing from a list of row verbs would go on losing rows
  without a sign.
- It is Postgres's and MySQL's only. SQLite and bytdb have no such
  statements, and their count comes from an Exec alone (`sqliteCounts`).
- A text holding several statements stays an Exec: the extended protocol a
  Query uses on Postgres refuses the pair, and a script's
  `s.Exec("CALL a(); CALL b()")` worked before.

**The count of a statement run as a Query (`runMaybe`)**

- Postgres: `pgTagTracer`, a pgx query tracer set on the pool's config. It
  is called with the statement's own context when the rows close, so
  `runMaybe` leaves an `*atomic.Int64` in that context and the tracer
  stores the command tag's count in it. Every other statement costs one
  failed context lookup.
- MySQL: `SELECT ROW_COUNT()` on the same connection (`mysqlMaybe`). A
  Session's two statements already share one; a pooled run checks a
  connection out for the pair and retries once on `driver.ErrBadConn`, as
  `RunNotices` does on Postgres.
- Postgres kindMaybe statements go out in `pgx.QueryExecModeDescribeExec`
  (passed ahead of the arguments), which describes on every run.

**Every result set (`readSets`, `model.Result.More`)**

- `Manager.run` was split: `query` → `readSets` → `readSet`. The first set
  is the Result; the further ones go in `Result.More`, each cut at
  `max_rows`. `Result.Sets()` is all of them in order.
- At most 50 further sets are kept (`maxMoreSets`); past that
  `Result.MoreCut` is set and the rest are left for `rows.Close` to
  discard. Only go-sql-driver/mysql has further sets.
- A procedure that raises after its first SELECT fails the statement (the
  error is `rows.Err()` after `NextResultSet`).

**Result tabs (workspace)**

- `runLocked` makes a landing per set, titled `CALL p() · 2/3`
  (`setSuffix`); the done note says "3 result sets, showing the last: N
  rows"; a cut logs a warning.
- `resultTab` gains `set`, `sets` and `nth` (the statement's number in its
  run). `placeRunLocked` has a second kind of slot group: when the same
  statement lands on a tab holding one of its sets, the slots are that
  statement's sibling tabs (same run, same `nth`), refilled in order, the
  ones with no set closed. A rerun's own tab is a slot even when pinned.
  A rerun titles from `baseTitle()`, so "· 2/3" does not double.
- A different statement landing on one of them replaces that tab alone.

**Headless**

- `runStatements` appends each set as a result at its statement's
  position; `export.RenderRun` renders a lone statement bare only when it
  has one result, so a lone `CALL` with two sets is two blocks bannered
  `1/1` (two envelopes in JSON). `noteTruncated` says when sets were cut.

**Docs**: README (result tabs; headless formats), the dbc skill
(`SKILL.md`, `scripting.md`), `sdb/sdbapi/api.json` regenerated.

## Decisions made without the user

Recorded as N-318 so they can be flipped:

| Decision | Chosen | Cost |
| --- | --- | --- |
| Which statements run as Query-then-decide | every verb in neither list | a round trip for an unlisted rowless statement |
| Cap on result sets per statement | 51, not configurable | a looping procedure's later sets are dropped, with a warning |
| Headless shape of a lone statement with several sets | a multi-result document | `-t json` gives envelopes, not a bare row array |
| Another statement landing on a set's tab | replaces that tab alone | its sibling tabs stay, stale |

## Notes

- The Exec path of the probe is what showed `(SELECT 1) UNION (SELECT 2)`
  losing rows; through dbc it never did. A probe that bypasses the code
  under test confirms the driver's behaviour, not the product's.
- pgx's `TraceQueryEnd` fires when the rows close, so `query` closes them
  explicitly before returning rather than leaving it to the defer.
- `database/sql`'s `NextResultSet` on a driver without further sets closes
  the rows and returns false, which is what the deferred `Close` did
  before, so a result cut at `max_rows` behaves as it did.
- The script API summary quotes the first sentence of each field comment
  of an exported type. `model.Result` now says so beside its fields.
- Commits are on main, one for the item (`9179296`), one for this doc and
  the list.
