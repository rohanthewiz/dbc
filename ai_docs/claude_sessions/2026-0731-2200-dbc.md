# bytdb support: built in dbc, ported upstream, released as v0.8.0

Session: 7c4053d7-be13-4677-8e07-f2d9c593085d

## What happened

Added [bytdb](https://github.com/rohanthewiz/bytdb) as a fourth driver in dbc,
a sibling to the embedded SQLite. bytdb ships a SQL frontend and a Postgres
wire server but had no in-process `database/sql` driver, and dbc's `Manager`
speaks only `database/sql` — so the work was an adapter.

It was written in dbc first (`db/bytdbdrv`), then — after a question from the
user about where it belonged — **moved upstream into bytdb itself** as the
`stdlib` package, released as **bytdb v0.8.0**. dbc is now down to a driver
alias and a catalog query, which is the part that is genuinely dbc's business.

## Why it moved upstream

The argument that decided it: `convert` is coupled to bytdb's type list.
bytdb's timestamp/date/uuid/jsonb/text[] types were added after the original
bool/int/float/string/bytes set, and they are the whole reason `convert`
exists — they ride on `int64`/`[]byte` runtime representations, so only the
column type says a number is a moment. That list is still growing. Living in
dbc, the next type bytdb adds renders as `fmt.Sprint` of its raw
representation, silently. Living in bytdb, the type switch sits next to the
`ColType` constants and their tests.

Supporting reasons: nothing in the package was dbc-specific; it costs bytdb no
dependencies (`database/sql` is stdlib, so unlike `pgwire` — which has its own
`go.mod` to keep pgx out of the core module — it can be a plain subpackage);
and the path-keyed engine registry matters *more* upstream, since any program
opening the same file twice hits btypedb's lock.

## bytdb: the `stdlib` package (commit `3d64020`, tag `v0.8.0`)

Registers bytdb as the driver `"bytdb"`. Beyond the straight port from dbc:

- **Real DSN parser.** `[file:]<path>[?sync=never&concurrent_writes=true&encryption_key=<hex>]`,
  mapping onto bytdb's three re-exported options. An unrecognized option is an
  error, not a no-op — a typo in a durability or encryption setting should not
  be something you discover from its consequences. Key material never reaches
  an error message.
- **Conflicting-options detection.** The dbc version keyed the registry on path
  alone, so a second DSN asking for encryption or concurrency would silently
  adopt an already-open engine that had neither. The option signature is now
  part of the check.
- **`convert` errors** on an unrecognized Go type instead of `fmt.Sprint`-ing
  it. Right for a display tool, wrong for a general driver, where a caller
  scanning into a typed destination is better served by a clear failure.
- **Both escape hatches.** `OpenEngine(e)` wraps an engine the caller already
  holds (necessary — the file cannot be opened twice) and never closes what it
  does not own; `Engine(ctx, db)` reaches the engine behind a `*sql.DB` for the
  ordered range and index scans SQL does not express.
- **`ColumnTypeScanType`** alongside `ColumnTypeDatabaseTypeName`, for sqlx and
  the ORMs.

### The OCC changes reworked one decision

The user had pulled major changes into bytdb mid-session: **OCC** — opt-in
concurrent writes, real isolation levels, SQLSTATE 40001. An earlier design
note ("bytdb transactions are serializable, so `BeginTx` can ignore the
isolation level") was no longer true. `BeginTx` now maps the four Postgres
levels onto `BEGIN` (READ UNCOMMITTED folding into READ COMMITTED) and refuses
`LevelLinearizable` rather than silently downgrading it. Added `IsRetryable`
for `bytdb.ErrTxConflict`, with a test asserting `errors.Is` survives the serr
wrapping — a broken chain would silently break callers' retry loops.

### Tests: 30, 86.6% coverage, race-clean

Coverage started at 79.8%. Reading for *behavioral* gaps mattered more than the
number; eight tests were added:

- **Encryption round-trip** — the biggest gap. `encryption_key` was only
  unit-tested at the parse level, so nothing proved DSN options actually reach
  `bytdb.Open`. Now: write encrypted, close, confirm it refuses no-key and
  wrong-key, and reads back with the right one.
- **`INSERT ... RETURNING`** — untested despite being what `LastInsertId`'s
  error message points callers at.
- **Failed statement inside a block** — aborts it, refuses everything but
  ROLLBACK, and the connection comes back out of the pool clean. Driver-owned
  pool hygiene, not bytdb's.
- **Savepoints**, reachable only as raw statements.
- **Prepared query and `tx.Stmt`** — `stmt.QueryContext` was at 0%: the old
  test prepared an INSERT then queried *unprepared*.
- **Pre-context driver interfaces** (`conn.Prepare`, `conn.Begin`,
  `stmt.Exec/Query`) — dead to database/sql, which always takes the Context
  variants, but required by the interfaces and all at 0%.
- **`convert` rejecting an unknown type**, **short rows reading as NULL**.
- Extended the column-type test from 4 types to all 10.

What is still uncovered is `driver.ErrBadConn` paths and nil-error guards.

## dbc changes (this commit)

- `db/manager.go` — `driverFor` maps `bytdb` onto `bytdbdrv.DriverName`, with
  the package imported as `bytdbdrv "github.com/rohanthewiz/bytdb/stdlib"`.
  The unknown-driver error now names all four.
- `db/catalog.go` — `Ctrl+T` catalog query for bytdb. It goes through
  `pg_class`/`pg_namespace` rather than `information_schema.tables`: both were
  probed against a live database, and `information_schema` lists base tables
  only, so views would have been silently missing. `relkind` supplies the
  `BASE TABLE`/`VIEW` value, keeping the same three columns as the other
  drivers.
- `db/bytdb_test.go` — six tests, scoped to what is dbc's: the driver alias,
  `Manager` integration, `renderVal` output for bytdb's types, `Session`
  BEGIN/COMMIT, the `ErrCanceled` mapping, and the catalog query finding both a
  table and a view. Driver behavior is tested upstream.
- `config/config.go`, `dbc.example.toml`, `README.md`, `sdb/sdb.go` — docs:
  four drivers, two of them embedded; `$1` placeholders for postgres/bytdb.
- `go.mod` — `github.com/rohanthewiz/bytdb v0.8.0`, resolved from the proxy.

Verified end-to-end with the real binary, not just tests: DDL, `serial` +
RETURNING, timestamps through both the text table and the CSV/JSON exporters,
persistence across restarts, a Go script with parameter loops and exports, and
a typo'd DSN option correctly rejected with the known options listed.

## Notes for next time

- **bytdb has no in-memory mode**, so its DSN is always a real path. That is
  why the zero-config `demo` connection stays on SQLite.
- **`INSERT ... RETURNING` shows `rows_affected`, not the returned rows.** dbc's
  `isQuery` keys off the leading verb, so this hits Postgres identically — it is
  pre-existing and uniform, not a bytdb regression. Fixing it would be a
  cross-driver change to `isQuery`.
- **A stale sibling checkout broke the workspace build.** `~/projs/go/btypedb`
  was 8 commits behind origin while `bytdb/go.work` used it, so `go build ./...`
  in bytdb failed on OCC symbols before any of this session's code was
  involved. Pulled to `3692710`. Worth checking `go.work` siblings first when
  bytdb suddenly will not build.
