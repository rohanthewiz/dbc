## N-184: the results fold away under a job tab's run page

- **Decision: fold the results; don't move ◷ Runs to the dialog.** The
  Runs dialog would leave the tab with nothing to show after ▶ Run, which
  is what the run page is mostly for.
- **How.** While the Runs face is up, `jobs.js` `setFace` tells the host
  (`runsFace`). `.app.job-runs` then hides `#splitter` and `#results`, and
  the editor pane, where the page is drawn, takes the column. The log
  stays below.
- **Clearing it.** `hide()` and `setMode` clear the class for other tabs.
- **◎ Open preview on this very tab** used to do nothing. It now switches
  to ⊞ Design, where the grid with the preview's rows is.
- **Checked** with a screenshot: the DAG, fragment timeline, node table
  and log are all in view, where the drilldown used to be below the

## N-185: run records keep what their pipelines showed

- **`PipelineRun.Shown`** keeps each result a pipeline showed: a preview
  sink's rows, and a go node's `s.Show`, since both pass through one
  callback.
- **The bounds:**
  - 50 rows (`MaxShownRows`), as the item suggested;
  - 500 runes a value (`MaxShownCell`);
  - 20 results per pipeline (`MaxShownResults`), since the record is
    rewritten every flush and read whole by listings.
- **Where kept.** `keepShown` runs in `runOne` beside the Sink or
  `JobRequest.Show` hand-off. A preview run keeps nothing: it is never
  recorded, and its rows are on screen.
- **Where shown:**
  - the run page: under the fragment's node table (`shownTable`, a
    scrolling box);
  - `Run.Tree` (`dbc run show`): names them;
  - `-t json`: carries the rows.

## N-170: pg_dump from Docker when no local one is new enough

- **A fallback, not a mode.** `LocateOrDocker` is `Locate` first. When
  that finds nothing new enough, Docker is tried, under four conditions:
  no tools directory was named, the server's major is known, Docker
  answers, and it is not Windows. The tools are then `postgres:<major>`'s
  (`Tools.Image`). Both `Prepare` (the UIs) and `dbc dump` use it.
- **How a tool runs.** `Run.run` builds its command through `command`,
  so pg_dump, and for split every pg_restore, runs as
  `docker run --rm -i --user UID:GID …`.
  - Mounted at their own paths, so the arguments mean the same inside:
    the output's directory (split: the output itself), the service file's
    temp dir, and the TLS files the connection names.
  - `-e PGSERVICEFILE -e PGPASSWORD` pass the variables by name, so no
    secret is in argv.
  - The image is pulled first, and the progress lines say so.
- **The network** (the item's caveat). `dockerConn` rewrites a loopback
  host to `host.docker.internal` and drops a loopback hostaddr; on Linux,
  `--network host` instead. A Unix-socket connection is refused with a
  hint.
- **Two touch-ups:**
  - The progress line said "from ." for a Docker run; it no longer does.
  - The closing line now adds a version note for an archive
    (`RestoreNote`): this machine's pg_restore 16 refuses a 17 custom
    archive ("unsupported version (1.16)", seen).
- **N-169 updated:** its hand check, which was waiting on this, can now
  use a 17 or 18 server.
